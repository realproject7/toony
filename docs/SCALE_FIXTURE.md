# Sixty-cut scale fixture

The fixture (#314) is a generator plus the numbers it produced. It builds a
synthetic sixty-cut episode into a scratch directory it owns and removes,
drives Toony's shipped stages over it through the real command surface, and
records three things per stage: the exit code, the whole-second wall-clock, and
the output volume. It proves mechanics. It is not quality evidence and it is
not visual acceptance.

> This fixture is synthetic. It proves that Toony's stages run in order at sixty
> cuts, how long each takes, and how much each emits. It proves nothing about
> whether the result is a webtoon. Its images are not artwork. They were never
> drawn and were never generated by a model. Its text is not a story. No result
> from this fixture is visual acceptance, quality acceptance, or evidence that
> Toony can produce an episode. It does not satisfy #243 and it does not change
> what `docs/CAPSTONE.md` certifies.

## Running it

The recorded run below predates #350. New runs measure and stitch at the
project's reference width (800 px when absent). Pass `--width 1200` to those
commands to reproduce the earlier composition width. Geometry-only planning
keeps its fixed default, and the raster memory limit is unchanged.

```bash
pnpm scale-fixture
```

That compiles `toony-cli`'s tests and runs the one file under
`packages/cli/src/__tests__/scale/`. It needs nothing outside the clone: no
network, no provider, no environment variable, no file the clone does not
carry. It exits non-zero when any stage fails, when the cut count read back off
the built project is not sixty, when the two plan forms disagree, when the lint
finding set changes, or when the record does not carry the clause above.

The same test file runs inside `pnpm test` for `toony-cli`, so
`./scripts/verify-release.sh` runs it once per Node major from a fresh clone.
Each run's record is in the retained `node-<major>-test.log`, on the lines
prefixed `scale-fixture:` and one `scale-fixture-record` line holding the whole
record as JSON. Read the run, not this file.

Every stage carries a liveness guard: 600 seconds for the stages that compose
the page, 120 seconds for the rest. Crossing one means the stage stopped making
progress, not that the machine was slow. No recorded timing is compared to a
budget, because a verdict that moved with the host's clock would move twice per
gate and would not be a verdict.

## What the sixty cuts are

Twenty beats of three cuts. Each beat declares one panel shape, one gap height
between its cuts, and the gap it opens on; the first beat opens on none. The
shapes, the gaps and the opening kinds are all different, so nothing the page
measures is a constant.

| What varies | Range the sixty cuts span |
| --- | --- |
| `panelAspect` | 0.58 to 1.95 widths, twenty distinct values |
| gap height, px on the 800 px column | 44 to 324 px inside a beat, 360 to 522 px opening one; 39 distinct values |
| transition kinds | `gutter`, `hard-cut`, `fade`, `scene-break`, `black_band`, `void`, `color_field`, `palette_shift`, `desaturate_repeat` |
| `shotType` | all five kinds, no two neighbours alike |
| source image height at 1200 px wide | 696 to 2340 px |
| source image bytes | 7.5 KB to 22.4 KB |

An image is a grey ramp, a grid, and three rectangles at three luminances,
placed by the cut's index, at exactly the declared shape. It depicts nothing.
It passes the shipped image checks because it is not uniform, not dark and not
flat, and the lint result below is asserted exactly so the next change to the
image code is found by a failing run.

## What one run recorded

Measured on the development Mac on 2026-10-13, Node 24, from a warm working
tree. The gate's own runs are the numbers to quote; this table shows the shape
of a run and the order of magnitude of each stage.

| Stage | Command | Exit | Seconds | What it emitted |
| --- | --- | --- | --- | --- |
| build | the fixture's own | 0 | 0 | 60 cuts, 59 transitions, 7 project files, 20 KB |
| validate | `toony validate --json` | 0 | 1 | valid, 147 chars |
| plan, declarations | `toony plan --episode --json` | 0 | 1 | 1200 x 107,871 px planned; gutterRatio 0.2154, gutterMedian 0.30, panelHeightMedian 1.18, panelHeightSpread 0.4249, panelsPerScreen 1.33 |
| plan, beats | `toony plan --spec --json` | 0 | 0 | 20 beats, 1.97 to 6.24 widths long; every metric equal to the declarations form to four decimals |
| import x60 | `runImportImage`, manual provider, in process | 0 | 2 | 60 assets, 833 KB; 60 ingest log entries, every one `source: manual`; every cut `draft` |
| lint | `toony lint --json` | 0 | 6 | 0 findings, asserted empty; 172 chars of JSON, 2 lines of text |
| lint-episode | `toony lint-episode <id> --json` | 0 | 6 | 0 findings, asserted empty; 176 chars of JSON, 2 lines of text |
| measure | `toony measure --episode --json` | 0 | 18 | page 800 x 71,911 px composed; gutterRatio 0.2798, gutterMedian 0.3288, panelHeightMedian 0.7613, panelHeightSpread 0.4804, panelsPerScreen 1.69 |
| export strip | `toony export <episode> --output strip` | 0 | 19 | one 800 x 71,911 PNG of 608 KB plus the manifest |
| export cuts | `toony export <episode> --output cuts` | 0 | 20 | 60 PNGs, 696 to 2340 px tall, 858 KB with the manifest |
| export webtoon | `toony export <episode> --output webtoon` | 0 | 19 | 79 JPEG parts, 800 px wide and at most 1280 px tall, 71,911 rows in all; 3.9 MB |
| export instagram | `toony export <episode> --output instagram` | 0 | 21 | 92 frames of 1080 x 1350 in 5 posts; 2.4 MB |

The measure and export rows are from a run on 2026-10-19, Node 24. The strip and
the measured page use the project's 800 px reference column.

The whole run took about two minutes. The import stage's two seconds are
ingest alone; drawing the sixty images took another 2.5 seconds and is recorded
separately as `drawMs`. Generation wall-clock is not measured by this stage or
by any other, because no model provider runs: that is the one number #243 calls
out as the expensive one, and this fixture does not have it.

The two plan forms agree because they describe one structure, and the run
asserts it within one percent in code. Their agreement proves the two forms
read the same episode. It does not pin the scale; only the cut count does.

The lint result is empty on both commands. It is asserted as empty, and the
stage's exit code, its output size and its text report's line count are
recorded beside it, because an empty result on its own is not evidence the
stage ran. Image analysis ran on all sixty assets: a skipped analysis would have
reported `image/pixel-analysis-skipped`, and none did.

## The page against the caps

| Figure | This page | Cap | Share of cap |
| --- | --- | --- | --- |
| page width x height | 1200 x 107,871 px | `RASTER_DIMENSION_MAX` 1,000,000 px per side | 10.8 percent of the height cap |
| page pixels | 129,445,200 | `CANVAS_PIXELS_MAX` 268,435,456 | 48 percent |
| one source image | up to 1200 x 2340 px, 22.4 KB | `IMAGE_PIXELS_MAX` 16,777,216 px, `IMAGE_FILE_BYTES_MAX` 32 MiB | 17 percent of the pixel cap |
| raster working set | not returned by any command | `EPISODE_RASTER_BYTES_MAX` 2 GiB | see below |

The byte figure `assertRasterBudget` enforces is computed inside the export
targets and is not returned to a caller, so this fixture cannot record it;
exposing it is a separate change with its own justification. On paper, at the
budget's own arithmetic of twelve bytes per page pixel plus four per source
pixel plus the encoded inputs, this page needs about 1.55 GB for its bands,
final canvas and output buffer, about 0.41 GB for its sixty sources and under
1 MB of encoded input, about 1.96 GB against a 2 GiB (2.147 GB) budget. The
composed stages passed the guard. A taller fixture or a wider export would be
refused, and that refusal would be the result to record and file, not a reason
to shrink the fixture.

## What it cannot prove

- Anything about quality. The images are structure; the result is not a page
  anyone would read.
- Generation time at sixty cuts. No model provider runs, so prompt fallback,
  lockstring injection, seed handling and the remote opt-in gate are not
  exercised either.
- #243. That ticket needs a public-safe original episode, an independent human
  visual review, and stage timings from a real generation run. Its acceptance
  box stays unchecked, and `docs/CAPSTONE.md`'s PASSED verdicts and dates do
  not change.

## Cost

About two minutes per run on the development Mac, twice per release gate. The
measure and export stages each compose a page of 129 million pixels, so the
gate's test stage now holds roughly 1.5 GB of raster working set for a few
seconds at a time. The verdict does not depend on that: the budget is fixed and
independent of the host's RAM, and a host that cannot meet the repository's
documented runtime requirements is not a host the gate is defined on.
